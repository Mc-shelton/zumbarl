Zumbarl backend architecture across five layers: client, API gateway, core services, data layer, and infrastructure.

Layer 1Client layer
Your React app. Talks only to the API gateway — never directly to services or databases. All requests carry a JWT token.
ReactAxios / FetchReact QueryZustandSocket.io client
Layer 2API gateway
Single entry point for all client requests. Handles routing, rate limiting, authentication verification, and request logging before anything reaches a service.
Node.js + Expressnginx reverse proxyRate limiterJWT verification
Layer 3Core services
Eight independent services each owning a domain. They communicate with each other through internal APIs or a message queue — never directly to another service's database.
Node.js microservicesREST + internal eventsBullMQ job queue
Layer 4Data layer
Three databases, each chosen for what it does best. PostgreSQL for structured relational data, Redis for fast caching and sessions, and S3-compatible storage for files.
PostgreSQLRedisS3 / Cloudflare R2Prisma ORM
Layer 5Infrastructure & external
Third-party services Zumbarl depends on. Each is abstracted behind an internal adapter so you can swap providers without touching service code.
M-Pesa Daraja APIAfrica's Talking SMSSendGrid emailCloudflareRailway / Render

JWT structure
Every request carries a JWT with the minimum information each service needs to make an access decision without a database call.
Payload fields
user_id · role · campus_id · company_id (if company) · transition_mode · issued_at · expires_at
Token lifespan
Access token: 15 minutes. Refresh token: 30 days. Safety events force immediate revocation.
Role-based access control
Every API endpoint declares which roles can access it. The gateway checks the token role before the request reaches a service.
Student standard
Can read own profile, apply to gigs, access campus features. Cannot post briefs or view other students' private data.
Student transition
All standard access plus pipeline dashboard, placement availability toggle, and runway program features.
Company standard
Post briefs, view applicant profiles, rate students, access own analytics. Cannot see students who haven't engaged with them.
Pipeline partner
All company access plus full pipeline dashboard, transition-ready student pool, placement offer capability.
Safety officer
Read-only access to safety reports and related gig context only. Cannot access any other user data.
Super admin
Full access. Every action is logged with timestamp and reason. Requires 2FA on every session.
Automatic role upgrades
Role changes that happen without manual intervention — triggered by platform events, not admin action.
Transition mode unlock
Score service emits an event when a student meets score + time thresholds. Auth service upgrades the role. Student's next token refresh includes the new role.
Alumni window activation
Triggered on graduation date stored in profile. Gig access closes, pipeline access stays open. 12-month TTL set automatically.
Pipeline partner upgrade
Company completes 3 verified gigs. Gig service emits event. Auth service upgrades company role to pipeline partner.

Three rules for the backend
These matter more than any specific technology choice.
Never trust the client
Every permission check happens on the server. The React app never determines what a user can do — it only reflects what the server says they can do.
Money is never lost
Every financial operation uses database transactions. If a payout fails halfway, the entire operation rolls back. Log every state change with before and after values.
Safety data is siloed
The safety service has its own database schema that no other service can query. A bug in the gig service should never be able to expose a safety report.
